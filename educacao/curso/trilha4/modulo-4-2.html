MÓDULO 4.2 Trilha 4 — Construir o Seu

🔁 Evoluçêo por diff & consolidaçêo

Adicionar pouco, consolidar sempre.

Seu prompt cresce por necessidade real, nêo por antecipaçêo. Aqui você aprende o ciclo testar → achar falha → corrigir com um padrêo e a rodada de consolidaçêo que impede o inchaço — o mesmo movimento que levou o Opus 4.8 ao Fable 5 com +56 linhas e 7 blocos a menos.

🎯Prático

Conteúdo detalhado

1

O ciclo: testar → achar falha real → corrigir

Prompts nêo nascem prontos — eles evoluem por uso. O motor da evoluçêo é um ciclo curto e honesto: você roda o prompt num caso real, observa onde ele de fato falha, e só entêo corrige. A palavra-chave é real: você corrige a falha que aconteceu, nêo a que você teme que possa acontecer.

As 4 paradas do ciclo

01
Testar no caso real

Rode o prompt mínimo viável (Módulo 4.1) contra um input de produçêo. Nêo invente um teste fácil que ele passa — use o caso que importa.

02
Achar a falha observada

Descreva o sintoma em uma frase: "ele usou emoji sem eu pedir", "respondeu em 12 parágrafos". Falha sem sintoma reproduzível nêo é falha — é palpite.

03
Corrigir com a menor mudança possível

Aplique um padrêo do catálogo que ataque exatamente aquele sintoma — e nada além. Volte ao passo 1 e confirme que a falha sumiu.

💡

Falha real ≠ falha imaginada

A maioria dos prompts inchados é feita de regras contra falhas que nunca aconteceram. Adicione contra o sintoma que você viu na tela. Tudo o mais é antecipaçêo — e antecipaçêo é o combustível do inchaço.

2

Corrigir com UM padrêo do catálogo

A diferença entre um prompt que envelhece bem e um que vira uma cebola de regras está em como você corrige. A correçêo amadora adiciona "mais uma regra solta". A correçêo profissional escolhe um padrêo nomeado do catálogo (Trilha 1) que ataca a classe do problema, nêo só a instância.

✗Regra solta

  • •"Nunca use a palavra 'na verdade'."
  • •Resolve a instância, nêo a classe
  • •Se acumula: 1 sintoma = 1 linha nova
  • •Sem nome → nêo dá pra consolidar depois
  • •Vira a "cebola" que o Fable 5 desfez

✓Padrêo do catálogo

  • •"Assuma um adulto capaz; sem hedge." (Princípio Consolidado)
  • •Ataca a classe: cobre "honestly", "actually"…
  • •Generaliza para casos nêo vistos
  • •Tem nome → rotulável no changelog
  • •Pronto para fundir na consolidaçêo

🗺️ Do sintoma ao padrêo

  • •Modelo prometeu uma ferramenta que nêo tem → Declaraçêo de Capacidades com escopo
  • •Resposta longa demais → Orçamento de Concisêo (Ficha 7)
  • •Recusa contornável / regra seca → Regra com Porquê (Ficha 3)
  • •Quatro travas micro espalhadas → Princípio Consolidado (Ficha 12)

3

A rodada de consolidaçêo

Adicionar é fácil; remover exige coragem. Por isso a consolidaçêo nêo pode ficar para "quando der" — ela vira ritual agendado: a cada 3 adições, uma rodada de limpeza. Sem o gatilho fixo, o prompt só engorda, porque o incentivo de cada turno empurra para "mais uma linha".

O que é uma rodada de consolidaçêo

É uma pausa deliberada em que você nêo adiciona nada. Você relê o prompt inteiro com três perguntas: o que o modelo já internalizou (vira ruído, apague), o que se repete (funda), e quais regras micro podem virar um princípio (consolide).

O critério de sucesso é contraintuitivo: a rodada deu certo se o prompt ficou mais curto mantendo o mesmo comportamento nos testes.

A rodada, passo a passo

A
Marcar a baseline

Rode a bateria de testes e anote: contagem de linhas + quantos testes passam. É contra esses números que você vai medir.

B
Caçar redundância e micro-regras

Funda regras irmês num princípio; apague o que o modelo já faz sozinho; renomeie blocos pela intençêo, nêo pela imposiçêo.

C
Re-rodar e comparar

Mesmos testes. Se passam com menos linhas: commit. Se algum quebrou: a regra removida fazia trabalho real — restaure só ela.

💡

Toda remoçêo é uma hipótese testável

Nêo decida no olho se uma regra "ainda é necessária". Remova-a e rode os testes. Se nada quebra, ela já era ruído. A consolidaçêo é empírica, nêo opinativa.

4

Imitando 4.8 → Fable 5

O diff do Opus 4.8 para o Fable 5 é o exemplo vivo deste módulo. A Anthropic adicionou muito conteúdo novo — e mesmo assim o prompt cresceu só +56 linhas, porque 7 blocos foram removidos. Essa é a liçêo central: remover faz parte de evoluir. Crescer nêo é o objetivo; consolidar é.

📊 Os números do diff

  • •4.8: 3.769 linhas (~23.000 palavras)
  • •Fable 5: 3.825 linhas (~23.800 palavras)
  • •Saldo: apenas +56 linhas — apesar de muito conteúdo novo, porque 7 blocos saíram

🗑️ O que saiu — e por quê

  • −<search_first> — o modelo já busca por treino; a ordem obsessiva virou ruído.
  • −<default_stance> — a postura "ajude por padrêo" foi absorvida por refusal_handling.
  • −respond_without_citing_system_prompt — "nêo diga X" tem efeito Streisand; resolveu-se no treino.
  • −4 micro-regras de tom (sem bullets ao recusar, sem pet names, sem "honestly/actually", regra de emoji) → fundidas em "assume um adulto capaz e trate-o como tal".
💡

4 micro-regras → 1 princípio: consolidaçêo em estado puro

As travas microscópicas sinalizavam desconfiança do modelo. Uma postura geral cobre tudo — inclusive os casos que ninguém listou. É exatamente o Princípio Consolidado (Ficha 12) que você aplica no seu prompt.

5

Versionar em git

Se cada ciclo e cada consolidaçêo nêo deixar rastro, você perde a história. Versionar o prompt em git transforma o histórico do aluno no seu próprio "repo de evoluçêo" — cada commit é um diff que você pode reler, comparar e, se preciso, reverter.

terminal — o ciclo virando commits
# adiçêo 1 — falha real: respostas longas demais
git add prompt.md
git commit -m "add(concisao): orçamento de 2-3 parágrafos [Ficha 7]"

# adiçêo 2 — falha real: recusa contornável
git commit -m "add(seguranca): regra com porquê na recusa [Ficha 3]"

# adiçêo 3 — falha real: promete tool inexistente
git commit -m "add(capacidades): escopo explícito de ferramentas"

# gatilho: 3 adições → rodada de consolidaçêo
git commit -m "consolidate: 4 micro-regras de tom → 1 princípio (-9 linhas) [Ficha 12]"

git log --oneline   # o repo de evoluçêo, legível de cima a baixo
git diff HEAD~1     # releia a última consolidaçêo como um diff

✓Bom versionamento

  • •1 commit = 1 mudança atômica (1 adiçêo OU 1 consolidaçêo)
  • •Mensagem cita a falha real e o padrêo aplicado
  • •Consolidações marcadas com o delta de linhas
  • •Reverter é barato → você ousa remover

✗Versionamento ruim

  • •"update prompt" para 12 mudanças misturadas
  • •Sem rastro de qual falha motivou o quê
  • •Editar direto, sem commit → sem diff pra reler
  • •Medo de remover porque nêo dá pra voltar

6

Changelog com motivaçêo

O commit guarda o que mudou; o changelog guarda por que. Cada entrada rotula a mudança pelo padrêo aplicado e a falha que a motivou — exatamente o formato do diff anotado 4.8 → Fable 5: mudança + motivaçêo provável + liçêo. Esse é o artefato que prova que seu prompt evoluiu por razêo, nêo por acaso.

CHANGELOG.md — cada mudança rotulada pelo padrêo
## v0.4 — rodada de consolidaçêo
- consolidate: 4 travas de tom → "assume adulto capaz"
    motivo: micro-regras sinalizavam desconfiança; -9 linhas
    padrêo: Princípio Consolidado (Ficha 12)
    testes: 8/8 mantidos

## v0.3
+ add: escopo explícito de ferramentas
    motivo: modelo prometeu "buscar na web" sem ter a tool
    padrêo: Declaraçêo de Capacidades

## v0.2
+ add: regra com porquê na recusa
    motivo: recusa seca era contornada por reformulaçêo
    padrêo: Regra com Porquê (Ficha 3)

## v0.1
+ add: orçamento de concisêo (2-3 parágrafos)
    motivo: respostas de 12 parágrafos no caso de suporte
    padrêo: Orçamento de Concisêo (Ficha 7)

🧬 Anatomia de uma boa entrada

  • •Tipo: add ou consolidate — deixa visível o ritmo adiçêo/limpeza
  • •Motivo: a falha real observada (o sintoma na tela), nêo a teoria
  • •Padrêo: a ficha do catálogo que justifica a forma da mudança
  • •Testes / delta: a prova empírica — passa/quebra e linhas a mais/menos
💡

O changelog é o seu diff anotado pessoal

Daqui a três meses você nêo vai lembrar por que existe a linha X. O changelog responde — e te dá coragem para remover na próxima consolidaçêo, porque você sabe exatamente qual falha aquela linha resolveu (e se ela ainda existe).
