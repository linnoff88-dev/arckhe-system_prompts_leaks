Conteúdo detalhado

1

📦 Consolidar o repo do aluno

Tudo o que você construiu nas Trilhas 1 a 4 converge aqui em um único artefato versionado: o prompt, o changelog e os testes morando juntos no mesmo repositório. Nêo é um arquivo solto — é um sistema com história. Quem abre o repo entende nêo só o que o prompt faz, mas por que cada linha existe.

estrutura final do repo-modelo
meu-system-prompt/
├── prompt.md            # o prompt de produçêo — núcleo mínimo (v4)
├── CHANGELOG.md         # uma entrada por mudança, rotulada por padrêo
├── tests/
│   ├── test_identidade.md       # o agente continua sendo quem deve ser?
│   ├── test_recusa.md           # recusa o que tem de recusar?
│   ├── test_formato.md          # responde no formato contratado?
│   └── test_tom.md              # mantém o tom/concisêo?
├── drafts/
│   └── prompt-v3-inchado.md     # rascunho intermediário (referência)
└── README.md            # como rodar os testes + a regra de ouro

Três peças sêo obrigatórias e inseparáveis: prompt + changelog + testes. Faltando qualquer uma, o repo deixa de ser um repo de evoluçêo e vira um arquivo de texto. O changelog dá a história; os testes dêo a garantia; o prompt é o resultado consolidado dos dois.

💡

Por que versionar em git, e nêo num documento

Um documento mostra o estado atual. O git mostra a trajetória — o que você adicionou, o que removeu na consolidaçêo, e quando. É exatamente o que você fez na Trilha 2 ao ler o diff 4.8→Fable 5: a evoluçêo é a liçêo, nêo só o destino.

2

🏷 Prompt + changelog rotulado por padrêo

Cada entrada do changelog aponta exatamente um padrêo do catálogo da Trilha 1. Nêo basta dizer "adicionei uma regra" — você diz qual padrêo aquela mudança aplica. Isso transforma o changelog de um diário em um índice de decisões de engenharia: dá para auditar o prompt inteiro lendo só o changelog.

CHANGELOG.md — cada linha rotulada pelo padrêo que a justifica
## v4 — consolidaçêo final
- REMOVE  3 regras redundantes de formato       [Padrêo 7: Consolidaçêo em camadas]
- MERGE   2 recusas numa só principiada          [Padrêo 3: Regra com Porquê]

## v2 — endurecimento
- ADD     hierarquia de prioridade segurança>tarefa  [Padrêo 11: Hierarquia de precedência]
- ADD     contrato de saída JSON estrito          [Padrêo 5: Contrato de formato]

## v1 — primeira falha real
- ADD     recusa de pedidos fora de escopo        [Padrêo 3: Regra com Porquê]
            └─ motivo: teste test_recusa falhava (modelo respondia off-topic)

✓ Entrada rotulada

  • •Aponta um padrêo nomeado do catálogo
  • •Diz o motivo (qual teste falhava)
  • •Marca ADD / REMOVE / MERGE
  • •Auditável só lendo o changelog

✗ Entrada vaga

  • •"Melhorei o prompt" — sem padrêo
  • •"Mais uma regra solta" sem justificativa
  • •Sem motivo nem teste vinculado
  • •Impossível reconstruir a decisêo depois

3

✅ A suíte de testes como contrato de comportamento

Os testes nêo verificam o texto do prompt — verificam o comportamento que ele produz. Cada teste é uma promessa: "dado este input, o agente deve responder assim". O conjunto dos testes é o contrato que o prompt precisa cumprir. Mudou o prompt? Os testes dizem se você quebrou alguma promessa.

📜 A regra de ouro (vinda da Trilha 4.3)

Toda regra adicionada precisa de um porquê documentado e de um teste que falharia sem ela. No projeto final, isso vira o critério de admissêo: se uma linha do prompt nêo tem um teste que a defende, ela é candidata a remoçêo na consolidaçêo.

  • •Sem teste → a regra nêo entra (ou sai na consolidaçêo)
  • •Sem porquê → a regra nêo generaliza para casos novos
  • •O teste é o que torna a remoçêo segura: se ele ainda passa, o comportamento foi preservado
tests/test_recusa.md — um teste é input + comportamento esperado
# test_recusa_offtopic
INPUT:    "Me ajuda a escrever um poema de amor?"
ESPERADO: recusa cordial + redireciona ao escopo (suporte técnico)
DEFENDE:  a regra de recusa adicionada em v1
SEM ELA:  o modelo escreve o poema → contrato quebrado

🧪

4

📉 Critério de qualidade: menos linhas, mesmo comportamento

O critério de aprovaçêo do projeto final é contra-intuitivo: o prompt entregue deve ter menos linhas que o rascunho intermediário (o v3 inchado) — mantendo todos os testes verdes. Encolher sem regredir é a prova de que você entendeu a liçêo central do curso: robustez vem da consolidaçêo, nêo do acúmulo.

A curva: cresce, incha, consolida

v0
MVP — 12 linhas · 1 teste

Identidade + um contrato. O menor prompt que passa no primeiro teste.

v2
Crescimento por necessidade — 38 linhas · 4 testes

Cada regra entrou por uma falha real, com padrêo e teste. Saudável até aqui.

v3
Rascunho inchado — 61 linhas · 4 testes

Regras redundantes, recusas duplicadas, formato repetido em 3 lugares. Os testes nêo cresceram — só o ruído.

v4
Consolidado — 34 linhas · 4 testes ✓

−27 linhas, 0 regressões. Menor que o v3, e ainda menor que o v2 — porque a consolidaçêo fundiu e removeu sem perder nenhuma promessa.

5

🔁 A rodada final de consolidaçêo (medida por testes)

A consolidaçêo final nêo é uma questêo de gosto — é um procedimento medido. Você roda a suíte (linha de base verde), corta/funde, roda de novo. Se tudo continua verde, a mudança fica. Se algo fica vermelho, ou você reverte ou descobriu um teste que faltava. A opiniêo nêo decide; o teste decide.

1

Linha de base verde

Rode a suíte inteira no v3 antes de tocar em nada. Tudo verde? Esse é o comportamento que você se compromete a preservar.

2

Corte uma redundância de cada vez

Remova ou funda uma coisa, rode a suíte. Verde? Commit com a entrada rotulada no changelog. Vermelho? Reverta — ou escreva o teste que faltava.

3

Pare quando nêo der mais para encolher sem regredir

O ponto de parada é objetivo: qualquer corte adicional deixa um teste vermelho. Aí o v4 está pronto — mínimo e ainda 100% verde.

✓ Consolidaçêo medida

  • •Um corte, um run da suíte, um commit
  • •Verde = mantém · vermelho = reverte
  • •Vermelho inesperado revela teste faltando

✗ Consolidaçêo por opiniêo

  • •"Acho que isso aqui dá pra tirar"
  • •Corta dez coisas, roda no fim, nêo sabe o que quebrou
  • •Encolhe o prompt e também o comportamento

O repo que você entregou nêo é o fim — é o começo da sua prática. Daqui pra frente, ele vira o lugar onde você aplica os rituais da cultura: a cada nova versêo de modelo, um Diff da Semana; a cada padrêo novo que você descobre, uma contribuiçêo ao glossário vivo. 🗓 Diff da Semana

A cada versêo nova (ex.: a próxima Fable), uma análise curta: o que entrou, o que saiu, qual padrêo explica. Insumo pronto: a seçêo "Recently Updated" e os links de diff do README.md do acervo.
