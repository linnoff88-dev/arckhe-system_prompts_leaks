TRACK 4

🚀 Building Yours

The track where everything becomes practice. You start from the minimum viable prompt — identity + one contract — and grows it through evolution by diff: each rule only gets added with a documented rationale and a test that justifies it. With each iteration, one consolidation cut what remains. Everything versioned in git, with a changelog, until it becomes your personal growth repo.

4.1 ~30 min

🌱 The minimum viable prompt

The smallest prompt that passes the first test: identity + one contract. Resist getting ahead of yourself and define "works" before adding more.

What it is:

A beginner’s impulse is to dump all the rules at once. Starting small is the opposite: the smallest prompt that already delivers value.

Why learn:

Every rule you don’t need anymore is still debt—dead code that confuses the model and hides the real cause of errors.

Key concepts:

Minimum viable · small surface = easy debugging · add only when there's a real need.

What it is:

Only two parts: who the agent is (identity) and what it commits to doing (a contract). Everything else is optional.

Why learn:

It’s the core that must be there. Without it, there’s no prompt; with more than that in v0, you’re already anticipating.

Key concepts:

Identity · single contract · irreducible core.

What it is:

Anticipating means writing a rule for a problem that hasn’t happened yet. It seems prudent, but it’s accumulated debt.

Why learn:

Speculative rules bloat the prompt, create conflicts, and obscure which rules really matter.

Key concepts:

YAGNI in prompts · rules only for real failures · avoid speculative accumulation.

What it is:

"Works" isn't a feeling. It's a concrete criterion—input + expected behavior—that says unambiguously whether v0 meets the contract.

Why learn:

Without an anchor test, you add rules blindly and never know whether the next line helped or hurt.

Key concepts:

Objective criterion · input→output case · anchor before growing.

What it is:

We built a complete prompt-v0 for an inbox triage agent — identity + 1 contract only, nothing else.

Why learn:

Seeing the assembled MVP makes the concept tangible: you can recognize what’s core and what would be premature.

Key concepts:

Triage agent · lean prompt · one paired test case.

What it is:

Two small files versioned in git: the prompt-v0 and the first test it passes.

Why learn:

It’s the foundation of your personal lab—the first and most important baseline in the evolution repo.

Key concepts:

prompt-v0 · anchor test · first commit.

4.2 ~35 min

🔁 Evolution by diff & consolidation

The prompt engine: test → find a real failure → fix it with ONE pattern from the catalog. After each round, consolidate and version it in git with a changelog.

What it is:

Prompts evolve through use. The engine is a short, honest cycle: run it on a real case, observe the failure, fix it.

Why learn:

Without the cycle, you "improve" the prompt in the dark. With it, every change comes from a real observed failure.

Key concepts:

Short cycle · real case · observed failure, not imagined.

What it is:

The mature correction applies a single pattern from the Trail 1 catalog — it doesn't pile on standalone rules.

Why learn:

It’s what separates a prompt that ages well from an increasingly hard-to-maintain “onion of rules.”

Key concepts:

One standard per fix · catalog · avoid layering up.

What it is:

A scheduled ritual: every N cycles, you stop adding and merge, cut, or rewrite redundant rules.

Why learn:

Adding is easy; removing takes courage. Without the ritual, the prompt only grows and never shrinks.

Key concepts:

Scheduled ritual · merge/cut · a prompt that breathes.

What it is:

The diff from Opus 4.8 to Fable 5: lots of new content added, and yet a leaner prompt where it mattered.

Why learn:

It’s real proof that evolution and consolidation can coexist: the provider adds and prunes in the same round.

Key concepts:

Official diff · add and prune · living reference.

What it is:

Every cycle and every consolidation become a commit. Git turns the prompt into an artifact with a traceable history.

Why learn:

Without version control, you lose the history and can't revert a rule that made things worse.

Key concepts:

Commit per change · readable diff · reversibility.

What it is:

Each changelog entry labels the change by the pattern applied and the failure that prompted it.

Why learn:

The commit records what changed; the changelog records why—and the why lets you review the decision later.

Key concepts:

Recorded rationale · pattern + failure · reviewable decision.

4.3 ~30 min

✅ Tests and the documented why

The golden rule: every rule needs a documented reason AND a test that would fail. Without that, it doesn’t make the cut. Measure with tests, not opinions.

What it is:

One sentence supports the entire path: every added rule needs a documented reason AND a test to justify it.

Why learn:

It’s the filter that keeps the prompt lean and auditable—without it, rules creep in out of habit and never leave.

Key concepts:

Why + test · input filter · auditable prompt.

What it is:

It's not a code unit test — it's an input case plus expected behavior that would fail without the rule.

Why learn:

If you can't write the test that would fail, the rule has no measurable effect — and is probably unnecessary.

Key concepts:

Failing test · input→output · measurable effect.

What it is:

The prompt has a gate, and the test is the key. A rule without a test stays in the queue — not in the prompt.

Why learn:

It seems rigid, but that's what prevents the pileup from coming back: nothing gets added without evidence that it makes a difference.

Key concepts:

Entry gate · test = key · rule in queue vs. in prompt.

What it is:

Connects directly to Pattern 3 (Rule with a Reason): a bare prohibition is followed literally but fails outside the exact case.

Why learn:

The reason gives the model the principle, not just the instance — that's what makes the rule apply to cases you haven't written.

Key concepts:

Principle > blanket prohibition · generalization · Pattern 3.

What it is:

The deliverable: a minimal test suite linked to the changelog—a test for every rule worth keeping, no more and no less.

Why learn:

Links each rule to its evidence and rationale, closing the loop between prompt, test, and history.

Key concepts:

Minimal suite · 1 test per rule · prompt↔changelog traceability.

What it is:

The golden rule mirrors the providers’ direction: the industry moved from "more rules" to "measured rules."

Why learn:

Test-based decisions are reproducible and defensible; opinion-based decisions lead to endless debate.

Key concepts:

Evidence > opinion · reproducibility · market-aligned.

4.4 ~30 min

🚀 Versioned Final Project

Everything comes together: prompt + changelog labeled by pattern + test suite in a versioned repo. Final criterion: fewer lines, same behavior.

What it is:

Everything you built in Tracks 1 through 4 comes together in a single repo: prompt, changelog, and tests all in one place.

Why learn:

A cohesive, versioned artifact is what you take into the real world — ready for maintenance and review.

Key concepts:

Cohesive repo · prompt + changelog + tests · final artifact.

What it is:

Each changelog entry points to exactly one pattern in the Track 1 catalog—it’s not enough to say "I added a rule".

Why learn:

Labeling by pattern connects your practice to theory and makes every decision verifiable against the catalog.

Key concepts:

Pattern label · T1 catalog · traceable decision.

What it is:

The tests don't verify the prompt text—they verify the behavior it produces. Each test is a promise.

Why learn:

Testing behavior (not words) lets you rewrite and trim the prompt without worrying about breaking what matters.

Key concepts:

Behavior contract · input→output · refactor safely.

What it is:

The approval criterion is counterintuitive: the submitted prompt must have fewer lines than the intermediate draft.

Why learn:

Trimming while keeping all tests green proves maturity—you say the same thing with less.

Key concepts:

Density > volume · green test suite · concision as a goal.

What it is:

This isn't a matter of taste; it's a procedure: run the suite (starting from green), cut or merge, then run it again — it only counts if it stays green.

Why learn:

Consolidating by measuring with tests removes the fear of cutting: the suite tells you right away if you broke something.

Key concepts:

Green baseline · cut→rerun · measured procedure.

What it is:

The delivered repo isn't the end — it's the start of your practice, the place where you apply the track's rituals from now on.

Why learn:

Internalizing the rituals (cycle, consolidation, golden rule) is what separates those who took the course from those who actually maintain prompts.

Key concepts:

Living repo · ongoing rituals · practice beyond the course.
