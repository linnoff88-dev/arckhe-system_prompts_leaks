📦 Consolidate the student’s repo

Everything you built in Tracks 1 through 4 comes together here in a single versioned artifact: the prompt, changelog, and tests living together in the same repository. It's not a standalone file — it's a system with a history. Anyone who opens the repo understands not only what the prompt does it, but why each line exists.

final template repository structure
meu-system-prompt/
├── prompt.md            # o prompt de produção — núcleo mínimo (v4)
├── CHANGELOG.md         # uma entrada por mudança, rotulada por padrão
├── tests/
│   ├── test_identidade.md       # o agente continua sendo quem deve ser?
│   ├── test_recusa.md           # recusa o que tem de recusar?

Three parts are mandatory and inseparable: prompt + changelog + tests. Without any one of them, the repo stops being an evolution repo and becomes a text file. The changelog tells the story; the tests provide the assurance; the prompt is the consolidated result of both.

💡

Why version in git, not in a document

A document shows the current state. Git shows the trajectory — what you added, what you removed during consolidation, and when. That's exactly what you did in Track 2 when you read diff 4.8→Fable 5: the evolution is the lesson, not just the destination.

🏷 Prompt + changelog labeled by default

Each changelog entry points to exactly one pattern from the Track 1 catalog. It’s not enough to say "I added a rule" — you say which pattern that change applies. This turns the changelog from a diary into a engineering decision index: you can audit the entire prompt by reading only the changelog.

CHANGELOG.md — each line labeled with the pattern that justifies it
## v4 — consolidação final
- REMOVE  3 regras redundantes de formato       [Padrão 7: Consolidação em camadas]
- MERGE   2 recusas numa só principiada          [Padrão 3: Regra com Porquê]

## v2 — endurecimento
- ADD     hierarquia de prioridade segurança>tarefa  [Padrão 11: Hierarquia de precedência]
- ADD     contrato de saída JSON estrito          [Padrão 5: Contrato de formato]

## v1 — primeira falha real
- ADD     recusa de pedidos fora de escopo        [Padrão 3: Regra com Porquê]
            └─ motivo: teste test_recusa falhava (modelo respondia off-topic)

✓ Labeled input

  • •Points to a named pattern in the catalog

  • •Mark ADD / REMOVE / MERGE

✗ Vague input

✅ The test suite as a behavior contract

The tests don't verify the text of the prompt — they verify the behavior that it produces. Each test is a promise: "given this input, the agent should respond this way." The set of tests is the contract that the prompt must meet. Changed the prompt? The tests tell you whether you broke a promise.

📜 The golden rule (from Track 4.3)

Every rule you add needs a documented why and a test that would fail without it. In the final project, this becomes the admission criterion: if a prompt line has no test to defend it, it's a candidate for removal during consolidation.

  • •Without a test → the rule doesn't get included (or gets removed during consolidation)
  • •Without a reason → the rule doesn't generalize to new cases
  • •The test is what makes removal safe: if it still passes, the behavior has been preserved
tests/test_recusa.md — a test is input + expected behavior
# test_recusa_offtopic
INPUT:    "Me ajuda a escrever um poema de amor?"
ESPERADO: recusa cordial + redireciona ao escopo (suporte técnico)
DEFENDE:  a regra de recusa adicionada em v1
SEM ELA:  o modelo escreve o poema → contrato quebrado

📉 Quality criterion: fewer lines, same behavior

The final project’s approval criterion is counterintuitive: the submitted prompt must have fewer lines than the intermediate draft (the bloated v3) — keeping all tests green. Shrinking without regressing is proof that you understood the course’s central lesson: robustness comes from consolidation, not accumulation.

The curve: grow, bloat, consolidate

v0
MVP — 12 lines · 1 test

Identity + one contract. The shortest prompt that passes the first test.

v2
Growth by necessity — 38 lines · 4 tests

Each rule was added in response to a real failure, with a pattern and a test. So far, so good.

v3

Redundant rules, duplicate refusals, format repeated in 3 places. The tests didn’t grow — only the noise did.

v4

🔁 The final consolidation round (measured by tests)

The final consolidation isn't a matter of taste — it's a measured procedure. You run the suite (green baseline), cut/merge, and run it again. If everything stays green, the change remains. If anything turns red, you either revert or you’ve discovered a missing test. Opinion doesn’t decide; the test decides.

1

Green baseline

Run the full suite on v3 before touching anything. All green? That's the behavior you're committing to preserve.

2

Cut one redundancy at a time

Remove or merge a thing, run the suite. Green? Commit with the entry labeled in the changelog. Red? Revert — or write the test that was missing.

3

Stop when it can't be made any smaller without causing regressions

The stopping point is objective: any further cut makes a test fail. Then v4 is ready — minimal and still 100% green.

✓ Measured consolidation

  • •One cut, one suite run, one commit
  • •Green = keep · red = revert
  • •Unexpected red reveals a missing test

✗ Opinion-based consolidation

  • •"I think we can remove this"
  • •Cuts ten things, runs at the end, doesn't know what broke
  • •Shrinks the prompt and also the behavior
