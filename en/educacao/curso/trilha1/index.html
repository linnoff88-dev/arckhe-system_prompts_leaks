1.1 ~30 min

🧬 Anatomy of a System Prompt

The 6 universal sections that structure any effective system prompt — from identity to dynamic context — dissected in real prompts.

What it is:

The persistent instruction layer that defines the model's behavior before any user message — composed by the harness from stable and dynamic parts.

Why learn:

Distinguishing a system prompt from a user message, RAG, tool context, and a system-reminder is the prerequisite for reading any prompt without confusing the layers.

Key concepts:

Stable prompt · turn-by-turn messages · harness · dynamically injected context.

What it is:

The prompt’s anchor: persona + product, base model, and knowledge cutoff, stated in the first line.

Why learn:

Without an anchor, the model drifts — it becomes a different persona, invents capabilities, or talks about events beyond its cutoff as if it knew about them.

Key concepts:

Persona · base model · knowledge cutoff · mission scope ("your job is…").

What it is:

Structured list of tools with scope and usage conditions—not a vague paragraph.

Why learn:

A weak declaration leads to over-promising (offering what it can’t do) and under-using (ignoring what’s available). The structured spec solves both.

Key concepts:

Tool scope · usage condition · function signature · anti-overpromising.

What it is:

The section that states refusals and principles, positioned early to signal precedence: safety before usefulness.

Why learn:

A blanket prohibition can be bypassed; a rule with a rationale and a description of the pattern (not the mechanics) generalizes to new situations.

Key concepts:

Principled refusal · safety > helpfulness hierarchy · default vs. mechanics · early positioning.

What it is:

Concision budget, lists vs. prose, markdown use, and conversational vs. technical tone — the tone_and_style section.

Why learn:

Prevents two opposing anti-patterns: overly long responses and responses broken into bullets without coherent prose.

Key concepts:

Concision budget · prose vs. list · contextual markdown · tone calibrated to the product.

What it is:

The layer the harness injects each turn via <system-reminder>: date, user, notices — separate from the stable prompt.

Why learn:

Confusing what is stable with what is injected leads to incorrect conclusions when reading a leaked prompt and comparing versions.

Key concepts:

Harness · system-reminder · current date injected · stable/dynamic separation.

🧱 Structural Patterns

The 5 patterns that give the prompt its FORM—the skeleton that appears before any behavioral rule, regardless of domain.

What it is:

The distinction between patterns that give shape (skeleton) and those that shape behavior (voice), with the 5 structural patterns in this module.

Why learn:

The structure is what you can diff across versions and providers — it makes prompts readable and versionable.

Key concepts:

Skeleton · domain-independent · 5 patterns · diffable.

What it is:

"You are X" + model + cutoff date: the first pattern and the only one seen in 100% of prompts.

Why learn:

Identity is an anchor, not a biography—recognizing the pattern helps avoid the anti-pattern of a buried or bloated persona.

Key concepts:

Persona · knowledge cutoff · mission scope · 100% universal.

What it is:

Structured list where each capability includes "what it does," "when to use it," and "limits"—even as a function signature.

Why learn:

Seen at xAI, Google, Microsoft, Notion, Cursor, and Claude Code—more elaborate in agents than in pure chatbots.

Key concepts:

Scope · condition ("if the user…") · signature (params + defaults) · anti-overpromising.

What it is:

Each logical block wrapped in a named XML tag (<policy>, <tone_and_formatting>), flat and modular.

Why learn:

It’s what makes a prompt with thousands of lines maintainable and the diff between versions readable—in code, Markdown headers serve this purpose.

Key concepts:

Named block · flat (≤ 2 levels) · diffable · Markdown too.

What it is:

The <system-reminder> block injected by the harness, separate from the prompt's stable behavior.

Why learn:

Recognizing the dynamic layer prevents attributing to the "model prompt" what is actually runtime context.

Key concepts:

system-reminder · harness injection · separate layer · runtime context.

What it is:

The stated precedence that resolves conflicts: core policy > system > user > default.

Why learn:

Without an explicit hierarchy, conflicting instructions leave behavior undefined — the prompt needs to say which one wins.

Key concepts:

Declared precedence · core policy · conflict resolution · combination with <policy>.

🗣️ Behavioral Patterns

The patterns that give the model a VOICE—how it acts, decides, and speaks: rules with reasons, ALWAYS/NEVER contrasts, tool contracts, and consolidated principles.

What it is:

The shift from the skeleton (form) to the patterns that govern how the agent acts, decides, and expresses itself.

Why learn:

It’s where the agent’s personality and reliability live—the difference between a prompt that “obeys” and one that “understands.”

Key concepts:

Voice · behavior × structure · decision governance · expression.

What it is:

Every rule comes with the reason behind it, instead of a blunt command.

Why learn:

The rationale lets the model generalize to unforeseen cases instead of obeying mechanically and failing at the edges.

Key concepts:

Explicit reasoning · generalization · edge-case robustness · intent over literal wording.

What it is:

Pair of instructions that sets the desired behavior and the prohibited behavior side by side, in uppercase for emphasis.

Why learn:

Contrast removes the ambiguity of the middle ground—the model knows exactly which pole to move toward and which to avoid.

Key concepts:

ALWAYS/NEVER · uppercase emphasis · desired/prohibited pair · ambiguity removal.

What it is:

Concrete demonstration of the expected behavior (input → output) paired with the abstract rule.

Why learn:

One well-chosen example establishes behavior better than three paragraphs of description—the model learns by imitation.

Key concepts:

Demonstration · input → output · learning by imitation · rule + example.

What it is:

Explicit instruction about the ideal response length and when to expand or cut back.

Why learn:

Without a budget, the model "pads things out"; with one, it calibrates density to the channel (terminal, chat, API).

Key concepts:

Target length · expand/cut · density by channel · anti-verbosity.

What it is:

The behavior rules for tools: when to call them, in what order, how to chain them, and when to stop.

Why learn:

Naming the tool isn’t enough—the usage contract is what prevents redundant, out-of-order, or unnecessary calls.

Key concepts:

When to call · order · chaining · parallelism vs. sequence.

What it is:

The rule to preserve verbatim passages that carry exact meaning — quotes, code, load-bearing values.

Why learn:

Summarizing or paraphrasing exact content introduces subtle errors; the pattern teaches the model what NOT to rewrite.

Key concepts:

Verbatim · load-bearing · faithful quote · do not paraphrase.

What it is:

A general principle that absorbs several specific rules into a single high-level instruction.

Why learn:

It’s the mature form of a prompt: instead of listing every case, it states the principle that covers them all—more robust and shorter.

Key concepts:

General principle · consolidation · high-level · robustness through abstraction.

⚠️ Anti-patterns

What NOT to do — recurring mistakes that sabotage a system prompt, from onion prompts to emphasis inflation, with the symptom and fix for each.

What it is:

The logic behind studying what goes wrong: each anti-pattern has an observable symptom and a known fix.

Why learn:

Knowing the name of the error speeds up diagnosis — you go from "the prompt feels off" to "this is an onion prompt."

Key concepts:

Named symptom · correction · diagnosis · error catalog.

What it is:

A prompt that grows by addition: every incident becomes a new rule, and nothing is ever removed or consolidated.

Why learn:

The layers contradict each other and bloat the context; the fix is to consolidate them into principles (see module 1.3) and prune.

Key concepts:

Growth through additions · internal contradiction · context inflation · pruning.

What it is:

"Never X" without explaining the intent—the opposite of a Rule with a Reason.

Why learn:

Without the reason, the model follows the letter but fails on nearby variations that violate the rule's spirit.

Key concepts:

Strict order · edge-case failure · letter vs. spirit · add the why.

What it is:

Safety implemented by listing prohibited terms/techniques instead of describing the pattern to detect.

Why learn:

The list can be circumvented with synonyms and still teaches what to avoid; describing the principle generalizes better and is safer.

Key concepts:

List of terms · circumventable · pattern over mechanics · robust principle.

What it is:

Two sibling anti-patterns: forcing lists/headers/emoji into everything, and putting policies, tone, and tools in running text.

Why learn:

One strips the prose down to a skeleton; the other makes the prompt impossible to version—both curated by the XML Compartment.

Key concepts:

Forced format · skeleton without prose · mixed blocks · compartmentalize.

What it is:

Overusing CAPS, “CRITICAL,” “ALWAYS,” and bold — until emphasis loses its value as a signal.

Why learn:

If everything is urgent, nothing is: the model can't prioritize. Emphasis is a scarce resource and should be spent carefully.

Key concepts:

Excessive CAPS · signal loss · sparse emphasis · prioritization.
